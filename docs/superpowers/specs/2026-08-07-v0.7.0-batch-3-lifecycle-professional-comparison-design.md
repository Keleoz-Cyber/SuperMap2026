# v0.7.0 第三批：案例生命周期、专业诊断解耦与跨实验比较

**状态：设计已获用户逐项确认，等待书面规格复核后进入实施计划。**

## 1. 目标

本批完成 v0.7.0 的最后一组业务流程，使统一案例工作台不仅能进入数据、实验和成果，还能正确处理案例回收、未完成数据准备、独立专业诊断和跨实验候选比较。

完成后：

- 只有用户上传案例可以进入回收站；内置电阻率、微震 CSV 预置和瓦斯卡不可删除。
- 回收站不自动过期，用户可恢复或再次确认后永久删除。
- 上传中断后从已有数据版本的实际状态继续，不要求重新上传已保存文件。
- 专业诊断直接从已验证数据版本进入，不再要求先创建实验或开启全局“专业模式”。
- 专业确认快照可一键带入新的普通 Kriging 实验。
- 同一数据版本、同一验证合同下，可以选择来自不同实验的 2～4 个成功候选进行统一比较；选择两个候选时继续复用既有专业深度比较。

第三批完成后，v0.7.0 功能范围完成；仍需独立审查和发布门验证后才能打标签和创建 Release。

## 2. 当前事实与约束

1. v0.7.0 第一批已将电阻率、微震预置和用户上传案例收束到同一 `CaseWorkspaceView`。微震产品入口使用受控 CSV 预置和官方普通 Kriging 成果；DAT 浏览器路由与 FastAPI 注册已移除，历史 DAT CLI、服务层和测试夹具保留。
2. v0.7.0 第二批已提供统一 NetCDF 原生体渲染、X/Y/Z 正交切片、剖面统计和切片 ZIP。第三批不得改写渲染协议、网格或资产身份。
3. 专业诊断后端已经以 `dataset_version_id` 为主体，具备诊断、确认快照、分析任务、异常提取、候选专业证据和两候选比较。第三批主要修复产品入口、恢复能力和跨实验聚合，不重写专业算法。
4. SQLite 当前为 v6。`cases` 没有生命周期字段；外键没有声明数据库级 `ON DELETE CASCADE`，因此永久删除必须显式构造依赖图并验证文件归属。
5. 当前 Experiment 的数据版本和验证合同位于不可变参数快照中。跨实验比较必须沿 Candidate -> Run -> Experiment 回溯并校验，不能信任前端提交的数据版本或指标。
6. 项目是本地单机应用，没有账户、权限角色和常驻调度器。回收站不得依赖自动过期任务。

## 3. 方案选择

### 3.1 扩展现有工作台与服务层（采用）

```text
CaseWorkspace
├─ CaseLifecycleService
│  ├─ trash
│  ├─ restore
│  └─ purge
├─ DataPreparationResolver
│  └─ next_action
├─ ProfessionalDiagnosis（既有服务）
│  └─ apply confirmation to experiment draft
└─ CandidateComparisonService
   ├─ 2～4 候选统一比较
   └─ 两候选专业深度比较（既有服务）
```

业务规则由后端服务层和公共 DTO 提供。Vue 只展示允许的动作，不自行推导删除资格、恢复步骤或比较兼容性。

### 3.2 新建第二套案例管理中心/专业模式（不采用）

这会复制第一批建立的工作台、导航和状态模型，并重新引入“普通模式/专业模式”上下文漂移。

### 3.3 前端拼装既有 API（不采用）

浏览器无法安全确定 SQLite 外键、文件所有权、运行中任务和验证指纹。把这些逻辑放在前端会导致状态不一致和误删风险。

## 4. SQLite v7 生命周期

### 4.1 Case 字段

在 `cases` 增加：

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `lifecycle_state` | string | `active`、`trashed`、`purging`；默认 `active` |
| `trashed_at` | nullable text | UTC ISO-8601；仅 `trashed`/`purging` 非空 |

增加按 `lifecycle_state` 的索引。读取旧 v6 数据库时，所有既有行迁移为 `active`。迁移必须在事务中执行并可重复启动；比 v7 更新的数据库继续拒绝启动。

不得把生命周期塞入 `config_json`。查询、唯一约束和恢复需要结构化状态。

### 4.2 永久删除操作表

新增 `case_purge_operations`：

| 字段 | 含义 |
| --- | --- |
| `id` | 操作 UUID |
| `case_id` | 逻辑案例 ID；不建外键，案例删除后仍保留回执 |
| `state` | `prepared`、`quarantined`、`committed`、`cleaned`、`rolled_back`、`failed` |
| `manifest_json` | 依赖 ID、相对工件名、数量和哈希；禁止绝对路径 |
| `receipt_json` | 删除计数、开始/完成时间、结果；不含业务数据 |
| `error_json` | 类型化失败；不含绝对路径 |
| `created_at` / `updated_at` | UTC ISO-8601 |

该表是崩溃恢复日志，不作为用户历史数据浏览功能。成功清理后只保留有界回执。

## 5. 案例回收站

### 5.1 删除资格

只有持久化 `Case` 且公开身份为 `user_upload`、配置不是 `read_only` 的案例可删除。

- `builtin_legacy` 电阻率/瓦斯：适配器层即拒绝。
- `builtin_preset` 微震：即使存在 Case 行，也由 `workspace_kind=builtin_preset` 和 `read_only=true` 双重拒绝。
- 前端无删除按钮不是安全边界；所有写端点必须重复判定。

存在以下任一任务时，移入回收站和永久删除均返回 `CASE_HAS_INFLIGHT_WORK`：

- 案例实验下 `queued`/`running` Run；
- 案例数据集或候选关联的 `queued`/`running` AnalysisJob；
- `creating` RenderAsset。

用户必须先取消并等待任务进入终态。服务端不在删除请求中隐式取消任务。

### 5.2 移入回收站

`DELETE /api/cases/{case_id}`：

1. 校验删除资格和在途任务。
2. 原子更新 `lifecycle_state=trashed` 与 `trashed_at`。
3. 不删除数据库行、上传文件、实验、结果、导出、专业工件或 NetCDF。
4. `GET /api/cases` 默认不返回该案例。
5. 普通工作台、数据、实验和结果写端点对该案例返回 HTTP 410 `CASE_TRASHED`。
6. 已知深链不得继续修改状态；回收站专用读取仍可显示名称、删除时间和依赖摘要。

重复删除同一 trashed 案例幂等返回当前回收站 DTO，不刷新 `trashed_at`。

### 5.3 回收站与恢复

新增：

```http
GET  /api/trash/cases
POST /api/cases/{case_id}/restore
```

恢复原子写回 `active` 并清空 `trashed_at`。所有 case/dataset/experiment/run/result/asset/export ID 保持不变；原结果 URL 恢复有效。恢复前重新校验案例仍是 `user_upload`，且不存在未完成 purge 操作。

回收站无自动过期、无后台定时清理。

### 5.4 永久删除

```http
POST /api/cases/{case_id}/purge
Content-Type: application/json

{"confirmation_name": "用户看到的完整案例名称"}
```

名称逐字符匹配，不接受只传 ID、通用 `DELETE` 文案或前端布尔值。名称不符返回 `CASE_PURGE_CONFIRMATION_MISMATCH`。

服务按以下顺序执行：

1. 要求案例已处于 `trashed`，再次验证身份与在途任务。
2. 从数据库回溯完整所有权图，生成稳定 manifest；任何断链、跨案例引用或未知路径都阻断。
3. 所有候选路径必须位于 `PlatformSettings` 的 datasets/results/exports/render-assets 等受控根目录内；拒绝符号链接越界和 `..`。
4. 写入 `case_purge_operations(state=prepared)`。
5. 用同文件系统原子 rename 把待清理文件移到 `data_dir/purge-quarantine/{operation_id}`，记录相对映射并转 `quarantined`。
6. 在单一 SQLite 事务中按外键拓扑显式删除子行、案例行，并把操作转为 `committed`。
7. 提交成功后删除 quarantine，操作转为 `cleaned`。
8. 提交前失败则把文件移回并标记 `rolled_back`；不产生半删除成功响应。

需要覆盖的所有权图至少包括：

```text
Case
├─ DatasetVersion
│  ├─ QualityReport
│  ├─ ProfessionalDiagnostic
│  │  └─ ProfessionalConfirmation
│  └─ 关联 AnalysisJob
├─ Experiment
│  └─ Run
│     └─ CandidateResult
│        ├─ FormalSelection
│        ├─ ProfessionalResultArtifacts
│        ├─ AnomalyExtraction
│        ├─ 关联 AnalysisJob
│        ├─ RenderAsset
│        └─ Export → Publication
└─ datasets/results/exports/render-assets 中的受控文件
```

启动恢复：

- `prepared` 且案例存在：标记失败或重新执行预检，不删除文件。
- `quarantined` 且案例仍存在：按 manifest 恢复文件并 `rolled_back`。
- `committed` 且案例已不存在：完成 quarantine 清理并 `cleaned`。
- manifest 不可验证：阻断自动动作，报告 `CASE_PURGE_RECOVERY_REQUIRED`；不得猜测路径。

## 6. 数据准备恢复

### 6.1 工作台 DTO

`GET /api/cases/{case_id}/workspace` 增加：

```json
{
  "data_preparation": {
    "state": "needs_upload",
    "dataset_id": null,
    "latest_validated_dataset_id": null,
    "next_action": {
      "step": "upload",
      "label": "上传数据",
      "url": "/cases/{caseId}/datasets/new"
    },
    "error": null
  }
}
```

允许状态：

| state | 条件 | 主操作 |
| --- | --- | --- |
| `needs_upload` | 无可恢复的未完成数据版本 | 上传数据 |
| `needs_mapping` | 最新未完成版本为 `uploaded` | 继续字段映射 |
| `needs_quality_review` | 最新未完成版本为 `mapped` | 继续质量检查/警告确认 |
| `ready` | 无更新的未完成版本，且存在 `validated` 版本 | 新建实验/专业诊断 |
| `blocked` | 文件缺失、哈希/所有权异常或未知状态 | 显式修复提示；无继续写操作 |

`primary_dataset` 继续表示最新可建模的 validated 数据版本；`data_preparation.dataset_id` 表示需要恢复的最新未完成版本。二者可以同时存在，不能因一次新上传未完成而让旧 validated 版本无法继续建模。

### 6.2 恢复目标

- 选择最新的非 abandoned 未完成数据版本作为恢复目标。
- 较早未完成版本只显示历史状态，不自动覆盖或删除。
- `uploaded` 已保存的源文件直接复用，不要求重新上传。
- `mapped` 已保存映射，重新进入质量步骤时后端从标准化数据重算/读取权威质量报告；不信任浏览器缓存。
- 路由仍复用 `/cases/:caseId/datasets/:datasetId/prepare`，通过后端状态决定当前步骤。
- 页面刷新、浏览器返回和直接打开深链必须得到同一恢复步骤。

### 6.3 放弃本次准备

```http
POST /api/datasets/{dataset_id}/abandon
```

只允许属于 active `user_upload` 案例的未完成数据版本。状态改为 `abandoned`，不删除案例，也不删除文件；文件随案例永久 purge 统一清理。validated 数据版本不可 abandon。

## 7. 专业诊断解耦

### 7.1 入口

案例工作台的数据区对每个 validated 数据版本提供两个并列命令：

- 新建普通实验；
- 专业诊断。

不增加全局“专业模式”开关。诊断仍以 `dataset_version_id` 为唯一数据主体。

### 7.2 诊断列表与恢复

新增：

```http
GET /api/datasets/{dataset_id}/professional-diagnostics
```

返回该数据版本的有界诊断摘要，按创建时间倒序，包含任务状态、诊断指纹、配置摘要、错误和可查看 URL。工作台展示最近诊断，并允许查看历史诊断；运行中、失败和成功状态均可恢复到既有诊断页。

创建、轮询、取消、重试、读取变异函数和确认继续复用现有 API。修改诊断配置产生新身份，不覆盖历史工件。

### 7.3 应用确认到实验

成功确认页新增“应用到新实验”：

```text
/#/cases/{caseId}/experiments/new
  ?dataset={datasetId}
  &professional_confirmation={confirmationId}
```

实验创建页：

- 自动选择且锁定匹配数据版本；
- 算法切换为 `ordinary_kriging`；
- 带入 `professional_confirmation_id`；
- `z_scale=1` 且不可与确认快照的规范各向异性叠加；
- 显示诊断、确认说明、参数来源和快照指纹；
- 其他邻域/验证/网格参数仍由用户确认后创建实验。

后端继续沿确认 -> 诊断 -> dataset 链验证所有权。跨数据版本、IDW 携带确认、确认不存在或诊断未成功均 fail-closed。

普通 IDW 和普通 Kriging 实验不要求先做专业诊断。

## 8. 跨实验候选比较

### 8.1 候选目录

新增：

```http
GET /api/datasets/{dataset_id}/comparison-candidates
```

后端从 Experiment 参数快照筛选属于该数据版本的实验，再沿 Run -> Candidate 读取候选。响应按实验分组，包含：

- candidate/result/run/experiment 逻辑身份；
- 算法和有界参数摘要；
- candidate/run 状态与 materialized 状态；
- RMSE、MAE、R2、Bias、公共有效数、NoData 数和运行时间；
- 验证合同摘要与指纹；
- 正式选择、官方结果或普通候选标记；
- 结果 URL。

只有成功且指标可验证的候选可选择；失败候选可在历史区查看但不进入比较。

### 8.2 2～4 候选统一比较

```http
POST /api/candidate-comparisons

{"candidate_result_ids": ["...", "..."]}
```

请求去重后必须有 2～4 个 ID。服务端忽略前端提交的任何算法、指标或数据集说明，全部从持久化身份链回读。

统一排名要求：

1. 所有 Candidate -> Run -> Experiment 链完整且成功；
2. `dataset_version_id` 完全相同；
3. 验证方法、折数、种子、holdout 配置和折分指纹一致；
4. 公共有效集身份与指标口径一致；
5. 指标均为有限值，R2 的既有 null 语义不得伪造为 0。

如果 2～5 不满足，HTTP 200 返回 `comparable=false`、稳定 `mismatches` 和每个候选的独立摘要，不返回排名。数据版本不同直接返回 409 `COMPARISON_DATASET_MISMATCH`，因为该端点不承担跨版本浏览。

可比较时确定性排序：

```text
RMSE 升序
→ MAE 升序
→ R2 降序
→ 规范参数 JSON UTF-8 字节序
→ candidate_result_id 字节序兜底
```

响应返回比较指纹，但本批不新增多候选比较持久化表；比较可从不可变候选和验证工件重复计算。

### 8.3 两候选深度比较

当用户在 2～4 候选中固定两个时，继续调用既有 `/api/professional-comparisons`：

- 残差分布；
- 逐折指标；
- 不确定性能力；
- 专业参数和工件差异；
- 兼容性指纹。

缺少专业工件按既有 capability 显示 `not_applicable`/`not_computed`，不得把缺失冒充失败或零值。

比较页不同时挂载多个 SuperMap iframe。每个候选提供独立结果页链接；避免 GPU、SDK 缓存和渲染状态互相影响。

后续类 DSI 通过 Algorithm 合同和公开参数摘要接入，不在 Vue 中硬编码 IDW/Kriging 两种算法。

## 9. 前端信息架构

### 9.1 首页与工作台

- `user_upload` 案例卡提供菜单中的“移入回收站”；内置卡不出现该命令。
- 首页提供回收站入口和数量，不把回收站案例混入正常案例网格。
- 工作台保留数据、实验、成果分区，增加生命周期动作、数据准备主操作、专业诊断状态和候选比较入口。
- 后端 DTO 决定按钮是否显示/禁用及错误原因；前端不按 case ID 分支。

### 9.2 回收站

回收站列表显示案例名称、删除时间、数据版本/实验/成果数量、恢复和永久删除。永久删除使用独立确认对话框，要求输入完整案例名称；不默认聚焦危险命令。

### 9.3 候选比较

- 候选表按实验分组，复选框限制 2～4 个。
- 主表展示统一指标、算法、参数和身份标记。
- 不兼容时在表上方显示具体字段差异，隐藏“最佳”徽标。
- 选择恰好两个后开放深度比较。
- 所有文字明确“同一数据版本/同一验证合同”，不得称为跨案例排行榜。

## 10. 错误合同

| 条件 | HTTP | 稳定错误码/响应 |
| --- | ---: | --- |
| 删除/恢复/清理内置案例 | 409 | `CASE_DELETE_FORBIDDEN` |
| 案例存在在途任务 | 409 | `CASE_HAS_INFLIGHT_WORK` |
| 普通接口访问 trashed 案例 | 410 | `CASE_TRASHED` |
| 恢复 active 案例 | 200 | 幂等返回当前案例 |
| purge 名称不匹配 | 422 | `CASE_PURGE_CONFIRMATION_MISMATCH` |
| purge 依赖断链、跨案例或路径异常 | 409 | `CASE_PURGE_BLOCKED` |
| purge 中断且无法自动判定 | 409/启动诊断 | `CASE_PURGE_RECOVERY_REQUIRED` |
| 数据准备文件/哈希/所有权异常 | 409 | `DATA_PREPARATION_CORRUPT` |
| abandon validated 数据版本 | 409 | `DATASET_ABANDON_FORBIDDEN` |
| 专业确认跨数据版本 | 409 | 沿用现有专业确认错误码 |
| 比较选择不是 2～4 个唯一候选 | 422 | `COMPARISON_SELECTION_INVALID` |
| 候选不属于同一数据版本 | 409 | `COMPARISON_DATASET_MISMATCH` |
| 验证合同/有效集不一致 | 200 | `comparable=false` + `mismatches` |

所有公共错误不得返回绝对路径、SQLite 行、私有文件名或未经有界化的大型 manifest。

## 11. 测试与验收

### 11.1 后端

- v6 -> v7 迁移、空库创建、重复启动和未来版本拒绝。
- user_upload 删除资格；builtin_legacy/builtin_preset 双重保护。
- trash 幂等、首页隐藏、深链 410、恢复后所有 ID 和链接不变。
- Run/AnalysisJob/RenderAsset 在途阻断。
- purge 全依赖图、数据库删除顺序和目录清理。
- 文件路径 containment、符号链接越界、跨案例引用和 manifest 破坏阻断。
- 在 quarantine 前、后和数据库提交后的崩溃恢复。
- `data_preparation` 五状态、validated 与更新未完成版本并存、abandon 后选择下一状态。
- 诊断列表归属、有界响应和无路径泄漏。
- 确认快照应用到 Kriging；IDW/跨数据版本/错误 z_scale 拒绝。
- 同数据版本跨实验候选目录；2～4 选择和确定性排序。
- 验证指纹、公共有效集或指标口径不一致返回不可比较。
- DSI 等未知未来合法 Algorithm DTO 不被前端/比较服务硬编码拒绝（当前不可创建 DSI）。

### 11.2 前端

- 三类案例删除按钮能力矩阵。
- 回收站、恢复、永久删除名称确认和失败保持。
- 工作台五种数据准备状态与唯一主操作。
- 页面刷新/返回后恢复同一步骤。
- validated 数据版本直接进入专业诊断。
- 确认后实验表单锁定 Kriging、dataset、confirmation 和 z_scale。
- 候选选择数量限制、跨实验分组、不可比较提示和两候选深度比较入口。
- 不出现微震 DAT 产品入口。

### 11.3 浏览器流程

Mock E2E 至少覆盖：

1. 创建上传案例 -> 中断于 mapping -> 返回工作台 -> 继续 mapping/quality -> validated。
2. 移入回收站 -> 首页隐藏 -> 回收站恢复 -> 原工作台恢复。
3. 回收站永久删除 -> 案例和深链不可达。
4. validated 数据 -> 专业诊断 -> 确认 -> 应用到 Kriging 实验草稿。
5. 两个不同实验的 2～4 候选统一比较和不兼容提示。

本批不触碰 SDK 渲染协议。既有真实 SDK live 门必须全绿；无需仅因生命周期 UI 变化重新生成像素证据，除非结果页或渲染组件发生变化。

## 12. 明确不做

- 删除或归档内置电阻率、微震 CSV 预置和瓦斯案例。
- 回收站自动过期、后台定时清理、账户/角色/权限系统。
- 移除历史 DAT CLI、派生服务层、测试夹具或历史运行数据。
- 类 DSI、瓦斯正式数据接入、系统统计分析中心。
- 全站 UI 重做、AI 预测、任意斜切面或跨案例空间融合。
- iServer 自动发布、真实 CRS 补造或渲染器回退。
- 跨数据版本/跨案例统一排名。

## 13. 实施边界

- 第三批从合并后的 `main` 新建实施分支和 worktree；不得继续在 PR #13 已合并分支开发。
- 每个逻辑任务按 TDD 独立提交，数据库迁移先于 API 和页面。
- 先建立后端生命周期/状态/比较合同，再接 UI；禁止以前端按钮隐藏代替后端保护。
- 不修改 v0.6.1/v0.7.0 既有正式成果、预置 CSV、官方选择或证据目录。
- 不合并、不打 v0.7.0 标签、不创建 Release，直到独立审查通过并收到明确指令。
