**状态：依据已确认的整改方向起草，等待书面规范复审。通过后作为 PR #14 合并前的完整整改规范，不拆分为两个产品阶段。**

本文是已实现第三批设计
`2026-08-07-v0.7.0-batch-3-lifecycle-professional-comparison-design.md`

发生冲突时，本文仅在以下范围内优先：

- “专业诊断”和“专业分析”的产品命名与用户路径；

## 2. 问题与根因

当前系统把三个不同生命周期阶段都冠以“专业”概念：

1. 数据版本上的变异函数、方向性和各向异性诊断；
2. 携带诊断确认创建普通 Kriging 实验；
3. 成果上的折分、残差、不确定性和异常分析。

由此产生以下用户可见问题：

- 案例工作台同时出现 3 个“新建实验”，用户无法判断入口是否不同；
- IDW 默认状态仍展示“专业诊断”，但该诊断只服务于普通 Kriging；
- “查看详情”和“专业诊断”跳到相同新建页，历史诊断身份丢失；
- 同一数据集只改变 `diagnosis` 查询参数时，Vue 复用组件但页面不重载；
- 已有成功诊断不会在实验页被识别，用户容易重复运行；
- 普通 Kriging 结果已有 RMSE、MAE、R2、Bias，却因没有增强专业工件而没有模型评估入口；
- 候选比较显示原始算法/参数键和重复配置，两个比较按钮的关系不清楚；
- 页面主要依赖首页级返回，数据版本、实验、成果之间缺少连续上下文。

另有一个阻断实验创建的后端合同缺陷：诊断确认允许三维 `dip_deg`、`roll_deg` 和 `major_vertical_ratio` 为空，而实验转换强制 `float(None)`，返回 `PROFESSIONAL_CONFIG_INVALID`。

## 3. 产品术语与业务规则

### 3.1 统一术语

| 现有名称 | 新名称 | 主体 | 时机 |
| --- | --- | --- | --- |
| 专业诊断 | 空间结构分析 | DatasetVersion | 建模前 |
| 专业确认/专业模式 | 采用分析建议 | Experiment 草稿 | 创建普通 Kriging 时 |
| 专业分析 | 模型评估 | CandidateResult | 建模后 |
| 比较候选 | 模型对比 | DatasetVersion 下的成功候选 | 多实验完成后 |

数据库表名、内部 Python 类名和既有 API 路径可以保留 `professional`，避免无收益迁移；所有用户可见文案、按钮、标题和错误下一步必须使用新术语。

### 3.2 算法适用性

- IDW 不适用变异函数确认与各向异性建议，页面不显示空间结构分析入口。
- 普通 Kriging 可以不做空间结构分析，称为“快速建模”。
- 普通 Kriging 可以采用一条已成功且属于当前数据版本的确认快照，称为“诊断辅助建模”。
- 空间结构分析是最终/报告级 Kriging 的推荐步骤，但不得成为普通 Kriging 的强制前置条件。
- 预置官方成果沿用其受控官方链；用户无需重新分析才能查看官方成果。

### 3.3 评估能力

- 每个成功 CandidateResult 都有基础模型评估：算法、参数、验证合同、RMSE、MAE、R2、Bias、公共有效数和 NoData 摘要。
- 折分检查、逐点残差、不确定性、异常区域和诊断参数来源属于增强评估。
- 缺少增强工件不等于成果失败，也不得隐藏基础评估。

## 4. 目标用户流程

```text
首页
  -> 案例工作台
     -> 数据准备/数据版本
     -> 新建实验
        -> 选择 IDW
           -> 配置并运行
        -> 选择普通 Kriging
           -> 快速建模
           -> 或查看/运行空间结构分析
              -> 确认建议
              -> 返回已锁定的 Kriging 草稿
     -> 实验运行与本实验排行榜
     -> 模型对比（同数据版本、跨实验）
     -> 成果工作台
        -> 体渲染/切片/导出/正式选择
        -> 模型评估（基础能力始终存在，增强能力按证据展开）
```

空间结构分析页不得成为孤立工作台。所有进入路径都携带案例与数据版本上下文，所有完成动作都有明确下一步。

## 5. 案例工作台

### 5.1 区域职责

工作台保留 4 个业务区，每个动作只能归属于一个区域：

1. **概览**：案例身份、坐标、单位、数据来源和主打/官方成果摘要；不放“新建实验”。
2. **数据**：数据准备状态、validated/abandoned 数据版本和空间结构分析状态；ready 状态不再产生实验按钮。
3. **实验**：唯一的“新建实验”主按钮、最近实验摘要和当前数据版本的“模型对比”。
4. **成果**：主打/官方成果、最近成果和查看入口。

当存在多个 validated 数据版本时，“新建实验”先要求选择数据版本；只有一个可用版本时直接带入该版本。不得在概览、DataPreparationPanel 和数据版本行重复渲染同名命令。

工作台 DTO 增加有界 `recent_experiments` 和 `recent_results`，各最多 5 条，
按 `created_at DESC, id DESC` 排序：

- experiment 摘要仅包含 ID、名称、算法、dataset ID、最新 Run 状态、成功候选数、时间和相对 URL；
- result 摘要仅包含 result/experiment ID、算法、物化状态、是否主打、时间和相对 URL；
- 不返回参数全集、指标大表、工件 manifest 或文件路径。

### 5.2 数据版本上的分析状态

每个 validated 数据版本显示一个空间结构分析状态：

| 状态 | 文案 | 主操作 | 次操作 |
| --- | --- | --- | --- |
| 无记录 | 未分析（Kriging 可选） | 无 | 空间结构分析 |
| queued/running | 分析中 | 查看进度 | 取消（沿既有任务能力） |
| succeeded、无确认 | 分析完成，待确认建议 | 查看并确认 | 重新分析 |
| succeeded、有确认 | 分析建议可用 | 查看/采用建议 | 重新分析 |
| failed/interrupted/canceled | 分析未完成 | 查看原因 | 重试或重新分析 |

“查看”必须使用 API 返回的历史 URL，并保留 `?diagnosis={id}`。“重新分析”才进入无 diagnosis ID 的配置状态。

## 6. 空间结构分析

### 6.1 页面模式

路由继续使用 `/datasets/:datasetId/professional-diagnosis`，但页面按 URL 身份分为两种模式：

- 无 `diagnosis`：新分析配置；
- 有 `diagnosis`：恢复指定历史分析的运行、失败或成功状态。

页面状态身份是 `(datasetId, diagnosisId)`，任一项变化都必须重载。加载使用单调请求序号或取消机制，旧请求的成功、失败和 finally 不得覆盖新路由。

### 6.2 信息层级

页面标题改为“空间结构分析”。首屏先说明：

- 此分析用于帮助普通 Kriging 判断变异函数和方向性；
- IDW 不需要；
- 分析不会修改原数据，也不会自动创建实验。

默认配置保留方向选择与推荐参数。`lag_count`、`min_pairs_per_bin`、`max_pairs` 等实现型字段放入“高级设置”，仍保留标签、边界和服务端严格校验。

### 6.3 确认与复用

成功分析展示证据、候选模型和各向异性建议。确认后主命令为“采用建议并创建克里金实验”，导航到：

```text
/#/cases/{caseId}/experiments/new
  ?dataset={datasetId}
  &professional_confirmation={confirmationId}
```

诊断列表/详情公共 DTO 增加有界 `latest_confirmation` 摘要，包含 ID、指纹、确认时间和可应用状态，不暴露路径或完整工件。存在多条确认时按
`created_at DESC, id DESC` 选择最新一条；不存在时为 null。已有确认时页面直接展示不可变快照并允许再次应用；重新分析或创建新确认不得覆盖历史记录。

## 7. 实验创建

### 7.1 普通入口

实验页加载数据版本后，先显示算法和参数。IDW 模式不渲染任何空间结构分析文案、入口、确认状态、邻域椭球或专业不确定性配置。

普通 Kriging 模式显示“建模依据”：

- `快速建模`：默认使用现有自动/手动变异函数参数；
- `采用空间结构分析建议`：按 `created_at DESC, id DESC` 选择当前数据版本最新的成功分析并进入其详情确认/复用；不存在成功分析时进入新分析配置。

该选择使用单选/分段控件表达，不使用全局“专业模式”开关。

### 7.2 携带确认的入口

存在 `professional_confirmation` 时沿既有归属链读取确认，服务端响应决定 case/dataset，不信任 query 中的 dataset：

- 算法锁定普通 Kriging；
- 数据版本锁定；
- `z_scale=1` 锁定；
- 显示可读的模型、方位、比例和来源摘要，原始 UUID/指纹降为详情；
- 搜索邻域与经验不确定性放在“高级参数”折叠区；
- 提交继续携带不可变 confirmation ID。

页面提供返回案例和返回空间结构分析的上下文链接。

## 8. 三维确认规范化

### 8.1 合同规则

`keep_isotropic=true` 继续生成规范各向同性变换。

`keep_isotropic=false` 时，对已被确认服务接受的水平证据进行以下规范化：

```text
dip_deg 缺失/null              -> 0.0
roll_deg 缺失/null             -> 0.0
major_vertical_ratio 缺失/null -> 1.0
```

`azimuth_deg` 和 `major_minor_ratio` 仍为必填。所有角度必须有限，所有比例必须有限且大于 0。规范化后再构造 `KrigingAnisotropySpec`。

该规则表示“没有证据支持额外垂向各向异性”，不是伪造垂向诊断。原确认 JSON 保持不可变；规范化结果进入实验参数来源与指纹计算，确保同一确认确定性地产生同一实验身份。

### 8.2 错误响应

只有缺少必填字段、非有限数值、比例非正或维度不匹配时返回 409 `PROFESSIONAL_CONFIG_INVALID`。错误 message 必须指出具体字段和允许的下一步，不返回 Python 异常文本或本地路径。

## 9. 模型评估

### 9.1 路由与兼容

新增用户路由 `/results/:resultId/evaluation`，页面标题为“模型评估”。旧 `/results/:resultId/professional` 作为兼容重定向保留，不再作为可见入口。

`GET /api/results/{result_id}` 增加有界 `evaluation_summary`。现有顶层
`algorithm`、`parameters`、`validation` 和网格 `nodata_count` 继续作为唯一来源，
不得在新增对象中重复：

```json
{
  "common_valid_count": 0,
  "candidate_valid_count": 0,
  "candidate_nodata_count": 0,
  "total_count": 0,
  "coverage": 0.0,
  "rmse": 0.0,
  "mae": 0.0,
  "r2": null,
  "bias": 0.0,
  "enhanced_evidence_available": false
}
```

数值来自已登记 Candidate/Run/Experiment 身份链，字段语义与既有
`CandidateMetrics` 一致。前端不得自行拼接或把 `r2=null` 转为 0。顶层
`nodata_count` 表示物化网格 NoData，`candidate_nodata_count` 表示验证候选 NoData，
两者不得混用。旧 `professional_analysis_supported` 可在内部兼容期保留，但用户能力
由 evaluation summary 与增强证据响应共同决定。

### 9.2 页面内容

所有成功成果显示：

- 评估结论摘要；
- RMSE、MAE、R2、Bias、公共有效数和 NoData；
- 验证方法、折数、种子/留出配置；
- 算法和主要参数来源；
- 返回成果工作台、实验和案例的导航。

增强证据存在时追加：结构分析来源、折分检查、残差、不确定性、异常区域和双候选详细比较。不存在时显示“基础评估可用；本结果未生成增强证据”，不得显示阻断页。

成果工作台始终展示“模型评估”入口，不再展示禁用的“仅生成专业证据……”说明。

## 10. 模型对比

### 10.1 用户表达

页面标题改为“模型对比”，副标题解释“同一数据版本和验证方法下比较不同实验结果”。合同指纹和 UUID 进入可展开详情，不作为主标题。

算法和参数使用中文可读格式：

- `idw` -> `IDW（反距离加权）`；
- `ordinary_kriging` -> `普通克里金`；
- 未知未来算法使用后端名称并安全截断；
- 参数显示为带单位/含义的键值，不直接输出原始 JSON 键串。

### 10.2 重复配置

候选目录为每个候选返回 `configuration_fingerprint`，由 dataset、algorithm、规范参数和验证指纹确定。UI 对同 fingerprint 的候选标记“相同配置，第 N 次运行”，不静默删除任何历史候选。

同一配置可以查看历史，但标准模型对比 UI 对每个 `configuration_fingerprint`
最多允许选择一个候选；用户尝试选择第二个时，页面说明它不会增加方法差异证据。
底层 2 至 4 candidate ID 比较 API 保持既有合同，不新增重复配置错误码；该限制属于
面向“方法差异”的产品交互，不改变历史数据和程序化比较能力。

### 10.3 命令层级

- 选择 2 至 4 个候选后只有一个主命令“开始对比”；
- 服务端返回不可比较时显示具体不一致字段，不给出最佳排名；
- 可比较时显示确定性排名；
- 恰好两个且都有增强证据时，在比较结果内提供次命令“查看详细差异”；
- 页面初始状态不并列展示“比较候选”和“深度比较”。

## 11. 导航与交互一致性

### 11.1 上下文导航

扩展共享导航组件，按可获得身份显示语义化路径：

```text
首页 > 案例 > 数据版本 > 空间结构分析
首页 > 案例 > 实验
首页 > 案例 > 实验 > 成果
首页 > 案例 > 实验 > 成果 > 模型评估
```

导航使用 `RouterLink`/链接语义，支持键盘、打开新标签页和复制地址。状态变更命令继续使用 button。不得只提供“返回首页”让用户丢失上下文。

### 11.2 可访问性与状态

- 异步错误使用 `role=alert`；非阻断状态更新使用 `aria-live=polite`；
- 所有自定义图标按钮有 aria-label 和键盘行为；
- 禁止没有替代焦点样式的 `outline: none`；
- 标题从 h1 到 h2/h3 连续；
- 表格表头与表体使用同一语义 table；
- 表单字段有 label、name、合适 input type 和 autocomplete；
- 桌面与 390x844 移动端不出现页面级横向滚动、文本遮挡或命令重叠。

## 12. API 与状态边界

本整改允许以下向后兼容扩展：

- 诊断列表项增加 `latest_confirmation`；
- ResultMetadata 增加 `evaluation_summary`；
- ComparisonCandidateSummary 增加 `configuration_fingerprint`；
- CaseWorkspaceSummary 增加有界 `recent_experiments` 和 `recent_results`；
- 工作台前端保存完整最新诊断摘要，而不再只保存 status 字符串。

不增加数据库表或 schema 版本，不修改已登记诊断、确认、候选、正式选择、网格、NetCDF 或专业工件。所有新增字段必须有 Pydantic/TypeScript 明确类型、有界文本和无绝对路径保证。

## 13. 错误与恢复

- 空间结构分析列表失败不阻断案例工作台，但显示“分析状态暂不可用”和重试，不得静默伪装为“未分析”。
- 历史 diagnosis 不存在返回明确 404；与数据版本不匹配返回 409，不回退到新建配置。
- confirmation 加载失败时禁用实验提交，保留返回分析页入口。
- evaluation summary 缺失或身份断链时成果渲染仍可查看，模型评估显示类型化错误和返回成果入口。
- 比较目录失败不清空为“暂无候选”；区分加载失败与真实空状态。
- 本整改涉及的工作台、实验、空间结构分析、模型对比和模型评估请求都使用最新请求守卫，旧 success/error/finally 不得覆盖当前身份。

## 14. 测试与视觉验收

### 14.1 后端

- 2D/3D 各向同性、水平各向异性、完整三维各向异性；
- nullable dip/roll/vertical ratio 的规范化与确定性指纹；
- NaN、Inf、零/负比例和缺少水平必填字段拒绝；
- 诊断历史 DTO 的 latest confirmation 归属、成功状态和无路径泄漏；
- 工作台 recent experiment/result 的排序、5 条上限、active-case 归属和无路径泄漏；
- evaluation summary 对 IDW、普通 Kriging、诊断辅助 Kriging、`r2=null`；
- configuration fingerprint 对相同/不同参数、验证合同和未来算法稳定。

### 14.2 前端单元测试

- 案例工作台在每个上下文只显示一个“新建实验”；
- data preparation ready 只显示状态，不产生实验命令；
- “查看空间结构分析”携带指定 diagnosis ID，“重新分析”不携带；
- 同一 dataset 的 diagnosis query 快速切换和 stale response 防护；
- IDW 零空间结构入口；普通 Kriging 展示快速/辅助选择；
- confirmation 草稿刷新后锁定算法、dataset、z_scale 并可提交；
- 所有成功结果都有模型评估，增强面板严格按能力显示；
- 重复配置标记、同配置选择限制和单一“开始对比”命令；
- breadcrumb 链接、焦点、alert/live region 和标题层级。

### 14.3 浏览器流程

Mock E2E 至少覆盖：

1. validated 数据 -> IDW 快速实验 -> 运行 -> 成果 -> 基础模型评估；
2. validated 数据 -> 普通 Kriging 快速实验 -> 基础模型评估；
3. validated 数据 -> 空间结构分析 -> 确认 -> Kriging 草稿 -> 运行 -> 增强模型评估；
4. 已有诊断从工作台查看详情，不新建诊断；
5. 同一数据集在新建/历史诊断 URL 间切换，页面身份正确；
6. 2 至 4 个跨实验候选对比、重复配置提示和双候选详细差异；
7. 首页、上传、回收站、恢复、永久删除、微震预置和电阻率既有流程不回归。

真实浏览器视觉验收覆盖用户上传、微震预置和 legacy 电阻率在 1440x900 与 390x844 的首页、案例工作台、实验、空间结构分析、模型对比、成果和模型评估。逐页检查命令唯一性、可读文案、无横向溢出和连续返回路径。

## 16. 完成定义

满足以下全部条件才可认为整改完成：

1. 用户可以用一句话理解空间结构分析：它是普通 Kriging 的可选建模依据，不适用于 IDW；
2. 用户在任一上下文只看到一个明确的新建实验主操作；
3. 历史分析、重新分析、采用建议和模型评估均有不同且可恢复的 URL 身份；
4. 报告中的三维 confirmation 可以成功创建实验，非法数值仍 fail-closed；
5. 每个成功成果都有基础模型评估，增强证据只增加能力、不阻断页面；
6. 模型对比能解释重复配置、可比性和详细差异的关系；
7. 三类案例、桌面/移动端和既有生命周期/渲染流程全部回归通过；
8. PR 保持 OPEN，等待独立复审和明确合并指令。
