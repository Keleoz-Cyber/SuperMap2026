# GeoModelingPlatform 文档整理设计

## 1. 目标

整理 `GeoModelingPlatform` 代码仓库中的 Markdown、文本提示词和开发交接文档，形成少量、清晰、互不冲突的正式文档。允许在一次任务中直接删除无用文件，但删除前必须将仍然有效且唯一的信息迁移到正式文档，并保证所有删除均可通过 Git 历史恢复。

## 2. 范围

只处理：

- 仓库根目录中的 Markdown 和文本提示词；
- `docs/`；
- `开发交接包/`；
- 测试目录中的说明文档，但仅在其确实重复或失效时处理。

明确不处理：

- 仓库外的 `../超图杯资料` 及其全部原始资料；
- Python 源代码、测试代码和配置；
- UDBX、原始 DAT、论文、表格和图片；
- 生成输出、日志和本地环境文件；
- Git 历史、标签和 Release。

## 3. 安全模型

整理必须在从当前 `main` 创建的新分支上进行。当前 `main` 包含尚未推送的本地设计提交，任务不得执行 reset、checkout 丢弃、rebase 改写或强制推送。

每份文档先分类为：

- `KEEP`：仍是正式入口、当前规范、架构、验收或决策依据；
- `MERGE`：存在唯一有效信息，但主体与正式文档重复；
- `DELETE`：内容已完全迁移、已失效、属于完成任务的临时提示词，或仅是重复副本。

删除可以在同一长程任务内直接执行，不需要再次等待人工确认。只有完成内容迁移、链接修复和差异验证后才能提交删除。

## 4. 目标信息架构

目标结构以以下入口为主：

- `README.md`：项目定位、快速开始、当前能力边界和正式文档导航；
- `docs/architecture.md`：当前系统架构和模块边界；
- `docs/acceptance.md`：当前验收方法；
- `docs/data/`：电阻率与微震数据规范、质量事实和未决问题；
- `docs/decisions/`：仍有效的架构与证据等级决策；
- `docs/status/`：当前里程碑、已验证成果和下一阶段门槛；
- `docs/superpowers/specs/`：仍会指导后续工作的设计说明。
- `docs/superpowers/plans/`：只保留尚未执行、仍会指导下一阶段工作的实施计划。

不建立仅用于容纳旧文件的 archive、legacy 或 backup 目录。真正失效且信息已迁移的文档直接删除。

## 5. 必须保留的信息

无论原文件最终保留、合并还是删除，以下信息不能丢失：

- 项目目标、MVP 范围、安装和 CLI 运行方法；
- Python 技术栈、模块边界和数据流；
- 电阻率 v0.1 已验证数据量、五模型验证口径和正式模型选择；
- `-9999` NoData 规则；
- SuperMap 的配置、文件、内部数据集和人工证据等级边界；
- 正式体元成果、水平切片、垂直切片和等值面的实际验证状态；
- 微震 v0.2a 的 22 个 DAT、2,006/2,005/1 统计链；
- W8 `1.#QNAN0` 的保留规则；
- W28 冲突登记和正式排除规则；
- 一维累计距离结果及无可信 X/Y/Z 的边界；
- `WL/2(km)`、测线几何、清洗规则和论文计数冲突；
- geometry、cleaning、interpolation downstream gates；
- v0.2b 数据确认设计；
- v0.2b 数据确认实施计划，并将其来源链接更新到整理后的正式文档；
- 原始资料只读和原始/派生数据分离原则；
- 尚未实现的瓦斯、DSI-like、垂直切片、等值面和数据集级 API 验证边界。

## 6. 优先审查对象

以下对象优先判断是否合并后删除：

- 根目录 `task_plan.md`、`findings.md`、`progress.md`；
- 已完成任务对应的 `KIMI3_MASTER_PROMPT.md` 和 `KIMI3_MICROSEISMIC_V0.2A_PROMPT.md`；
- `开发交接包/` 中与当前 README、architecture、acceptance 和 data 文档重复的内容；
- 已完成且不再指导后续工作的旧实施计划；
- 多处重复、数值口径过时或与当前代码冲突的状态说明。

优先审查不等于预先判定删除。必须完整阅读并登记唯一信息的迁移去向。

## 7. 冲突处理

当两个文档说法不同时，采用以下优先级：

1. 当前代码和自动化测试所验证的行为；
2. 已合并 PR 的验收证据和正式决策记录；
3. 当前数据审计报告；
4. 交接包与阶段进度文档；
5. 已完成任务的提示词和临时计划。

如果无法根据证据判断，不得自行选择一个版本。应保留冲突并在正式状态文档中登记，而不是删除其中一方后隐去问题。

## 8. 工作流程

1. 确认仓库、分支、HEAD 和工作区状态；
2. 从当前 `main` 创建 `chore/docs-consolidation-v0.2`；
3. 枚举所有目标文档并记录路径、用途、当前性和重复关系；
4. 输出机器可读或 Markdown 形式的内部分类清单；
5. 先建立目标目录和正式文档；
6. 迁移唯一信息并注明来源；
7. 删除已完成迁移的重复、临时和失效文档；
8. 修复 README 导航和全部仓库内部链接；
9. 搜索被删除文件名、过时口径和绝对本机路径；
10. 运行代码测试、链接检查、敏感文件检查和 `git diff --check`；
11. 审阅完整 diff，确认只含文档整理；
12. 分阶段提交、推送并创建 PR，不合并、不发布。

## 9. 删除审计

最终汇报必须逐项列出：

- 删除的文件；
- 删除理由；
- 其中有效信息迁移到哪个文件和章节；
- 如果没有迁移，说明该文件为何完全失效或完全重复。

同时列出所有新建、重写和保留不动的主要文档，避免只报告文件数量变化。

## 10. 验证要求

整理完成必须满足：

- `git diff --check origin/main...HEAD` 无输出且退出码为 0；
- 全量 pytest 通过；
- portable 和本地真实数据测试口径不退化；
- README 中的相对链接均能解析；
- 仓库中不存在指向已删除文档的引用；
- 不跟踪 DAT、PDF、XLSX、图片、UDBX、outputs、artifacts、logs 或密钥；
- `git diff --name-status` 不包含 Python、测试、配置和原始资料；
- 电阻率与微震关键统计在正式文档中各有唯一、明确的当前表述；
- 所有未决问题继续明确标记，不能因文档精简而被写成已解决；
- 工作区在提交后干净；
- PR 保持打开，不创建标签或 Release。

## 11. 完成状态

文档整理完成只表示信息架构和交接材料得到精简，不表示以下问题已解决：

- 微震二维/三维几何；
- `WL/2(km)` 到深度/Z 的换算；
- 微震正式清洗；
- 瓦斯数据标准化；
- DSI-like 插值；
- SuperMap 垂直切片、等值面或内部数据集级 API 验证。
